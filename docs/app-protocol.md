# 报文分析 APP 接口契约（v1）

> 本文档是手机 APP 与 ESP32 固件之间的唯一接口依据，两边各自开发，只靠这份契约对齐。
> APP 侧新会话开工时，以本文档为准，不需要继承固件会话的对话历史。

## 1. 系统角色

```
485 总线 ←→ BT04E(从机) ←→ [ESP32 主机/中继] ←→ [手机 APP]
                ↑________________直接连接_________↑
                    （同一时间 BT04E 只能被一个主机连）
```

- **ESP32**：蓝牙中继（收报文上屏 + 转发手机）、TF 卡报文落盘、按规则实时解码显示、接收 APP 下发的规则
- **APP**：连蓝牙收报文、AI 分析、编写协议规则、下发规则给 ESP32
- **ESP32 侧 AI 分析**：搁置为后续计划

## 2. 两种连接模式（APP 都要支持，做成两个入口）

### 模式 A：直连 BT04E（纯透传，分析用）

| 项 | 值 |
|---|---|
| 服务 | `FFE0` |
| 收（notify） | `FFE1` —— 模块转发的 485 原始字节 |
| 发（write） | `FFE2` —— 写入即上 485 总线 |

- BT04E 名称前缀默认 `BT04E`（可被 AT+NAME 改过）
- 有主机已连接时不响应 AT 命令；一次写入建议 ≤20 字节（模块串口波特率决定吞吐）

### 模式 B：连 ESP32（中继 + 控制，分析/运行两用）

| 项 | 值 |
|---|---|
| 服务（NUS） | `6e400001-b5a3-f393-e0a9-e50e24dcca9e` |
| 收（notify） | `6e400003-...cca9e` —— 报文/解析事件/命令响应，混流 |
| 发（write，无响应写即可） | `6e400002-...cca9e` —— 报文与命令 |
| MTU | 请求到 247；单次 write ≤244 字节，ESP32 自动分片 |
| 设备名 | `ESP32-S3-AI`（NVS 可改） |

**通道复用规则**：NUS 上跑两类数据——
1. **透传字节**：485 原始报文原样转发（ESP32 不加帧头，**无帧边界保证**，APP 自行按协议切帧）
2. **控制行**：以 `{` 开头、`\n` 结尾的单行 JSON 命令/事件。APP 发送侧注意：一条命令一次 write，确保 `\n` 结尾；解析时只把以 `{` 开头且 `\n` 结尾的片段当控制行，其余都是透传字节

## 3. 控制行协议（模式 B）

请求：`{"cmd":"...", ...}\n`；响应：`{"rsp":"...", ...}\n`；事件：`{"evt":"...", ...}\n`

| 命令 | 响应/事件 | 说明 |
|---|---|---|
| `{"cmd":"info"}` | `{"rsp":"info","fw":"1.3.1","relay":true,"conn":true,"rule":"电表03","log":true}` | 握手/查状态 |
| `{"cmd":"rule.set","rule":{...}}` | `{"rsp":"ok"}` / `{"rsp":"err","why":"..."}` | 下发规则，存 `/rules/<name>.json` 并立即生效 |
| `{"cmd":"rule.list"}` | `{"rsp":"rule.list","names":["电表03","..."]}` | 规则列表 |
| `{"cmd":"rule.get","name":"电表03"}` | `{"rsp":"rule.get","rule":{...}}` | 读回规则 |
| `{"cmd":"rule.del","name":"..."}` | `{"rsp":"ok"}` | 删除规则 |
| `{"cmd":"log.stop"}` / `{"cmd":"log.start"}` | `{"rsp":"ok","session":"log_1103_1432"}` | 手动停止/重新开始落盘会话 |
| `{"cmd":"dec.on"}` / `{"cmd":"dec.off"}` | `{"rsp":"ok"}` | 开关解析事件推送 |

事件（规则生效且 dec.on 时，每解析一帧推一行）：

```json
{"evt":"dec","t":49812345,"rule":"电表03","dev":1,"vals":["220.5","1.23","OK"]}
```
vals 顺序与规则 fields 一致；无法解析的字段填 `null`；多设备规则带 `dev`（设备地址），单设备规则不带。

## 4. 规则 JSON Schema（定稿，含多设备）

```json
{
  "name": "电表03",            // 规则名，唯一，即文件名
  "ver": 1,                    // 版本，每次修改 +1
  "src": "AI会话2026-11-03",   // 来源备注
  "addr": {"off": 0, "type": "u8"},   // 多设备：从帧里哪个字节取设备地址（省略=单设备）
  "match": [{"off": 0, "val": [1, 2]}],  // 可选：字节命中才解析（总线混有其他帧时防乱解）
  "crc": "modbus",             // 可选：CRC 校验通过的帧才解析（v2 实现，先预留）
  "fields": [
    {
      "name": "电压",           // 字段名
      "off": 3,                // 帧内字节偏移（0 起，含帧头）
      "type": "u16",           // u8/i8/u16/i16/u32/i32/f32/bit
      "be": 1,                 // 1=大端 0=小端（u16/u32 有效）
      "bit": 3,                // 仅 type=bit：位偏移 0-7
      "scale": 0.1,            // 原始值 × scale（可省，省=1）
      "unit": "V",             // 单位（可省）
      "enum": {"1":"合","0":"分"}  // 枚举映射（可省，命中则显示映射文本）
    }
  ]
}
```

多设备语义：
- 有 `addr` 时，解析引擎先读出设备地址，把解析结果归到该设备名下；各设备独立维护当前值；所有设备共用同一份 `fields`（同型号设备，最常见场景）
- 异构布局（每台设备字段不同）预留 `devs:{"1":[...],"2":[...]}` 替代 `fields`，v2 实现
- 事件与显示按设备分组；`evt:dec` 带 `"dev":<地址>`（单设备规则不带 dev 字段）

解析规则：ESP32/APP 收到报文后：match 命中（若有）→ 读 addr（若有）→ 按 fields 逐个取字节 → 按类型/字节序/位 → 乘 scale → 命中 enum 显示文本，否则数值+unit。两端逐字段语义必须一致。

## 5. 报文编码

- 透传字节永远是原始字节，ESP32 不改编码（GBK/UTF-8 转换只发生在 ESP32 的屏幕显示侧）
- APP 显示文本时按自身编码设置处理，hex 视图始终可用

## 6. 固件侧现状（APP 联调时参考）

- 仓库：`f:\ESP32\esp32s3`（GitHub: esp32-s3-ai-player / esp32s3-ai-chat），固件源码 `esp32/esp32_ai_chat/`
- OTA 推送：`POST firmware.bin → http://<设备IP>:8080/ota`；网页控制台 `http://<设备IP>:8080/`
- TF 卡落盘：`/logs/<会话>/frames.jsonl`（每帧一行 `{"t":ms,"rx":0/1,"len":n,"hex":"AA BB"}`）、`/logs/<会话>/decoded.csv`（开关）、`/rules/<名称>.json`、`/ai/<会话>.jsonl`
- 会话自动开/收尾：中继连上自动开，断开收尾；单文件 2MB 分卷

## 7. APP 侧待定项（新会话先定）

1. 技术栈：Android 原生 / Flutter / 其他（需要 BLE central + 后台收发，小程序 BLE 限制多，慎选）
2. AI 接口：厂商与 Key 存 APP 本地；报文喂给 AI 的格式建议直接给 hex + 帧长 + 方向，多帧给 JSONL 文件
3. 规则编辑器：AI 生成 JSON → 用户确认 → `rule.set` 下发

## 8. APP 内置规则解析器（必备能力，用于下发前调试）

APP 必须按第 4 节同一份 Schema **本地实现规则解析**，与 ESP32 逐字段语义一致（偏移/类型/字节序/位/缩放/枚举）。用途：

1. **生成即验证**：AI 生成规则草稿后，APP 对「刚收到的最近 N 帧报文」立即按草稿解析，用户在手机上直接看到解析值是否合理（数值范围、单位、枚举命中），确认无误再 `rule.set` 下发——不必先下发到 ESP32 再试错
2. **两端一致性比对**：规则下发后 ESP32 会推 `{"evt":"dec",...}` 事件，APP 把事件值与自己本地解析值比对，不一致说明规则有歧义或某端实现有偏差，当场暴露
3. **离线调试**：直连 BT04E 模式（模式 A）下 ESP32 不参与，APP 本地解析就是唯一的实时解码视图

调试视图建议：hex 原文 + 每个字段的高亮字节区间（off..off+len）+ 解析值列表，一眼对上「哪几个字节解析成了哪个值」。
